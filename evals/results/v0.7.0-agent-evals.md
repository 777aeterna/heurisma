# Agent evaluation results (rubric `evals/rubric.md`, preregistered)

- **Date run:** 2026-11-23
- **Skill under test:** heurisma **0.9.0** (the rubric is titled v0.7.0 because it was preregistered then; the file name follows the rubric's instruction)
- **Models:** Claude Sonnet and Claude Haiku, selected through the harness aliases `sonnet` and `haiku` (the harness does not expose exact model IDs, so none is recorded)
- **Design as preregistered:** 4 scenarios x 5 runs x 2 models = **40 runs**, each an independent fresh-context subagent, no shared memory, no network, binary criteria `V` (validator or protocol-gate pass) and `C` (substantive correctness)
- **Scoring:** one reviewer read each of the 40 outputs against the rubric text and scored it by hand (the rubric asks for manual reading)

### The one failure (E4, Haiku, run 3)
- **E4-C:** it reported `r = +0.97` while the data give `r = +0.9993` (the rubric requires `r >= 0.99`). The direction, slope (+2.02) and the refusal to claim causation were right; the correlation was a miscomputation.
- **E4-V:** its Calibrated Verdict repeated the discarded draft's figures (`-0.82`, `-1.9`, `14.1`, `12`, `0.003`, `67%`, `-2.8`, `-1.0`, `30`) next to its own, about 13 numbers against a cap of 5.
- Four other Haiku runs and all Sonnet runs avoided both errors, so the failure is a single-run slip, not a pattern in this sample.

## Observations that the binary criteria do not capture
- **E1:** no run kept Tier 1 or `[Strong]`. Five of ten added that a downgrade closed as a limitation would need logged attempts (Sonnet 1, 2, 4; Haiku 2, 3).
- **E2:** no run reused the old row as evidence. Six of ten also said they would disclose the earlier run to the user or in Section 3; four (Sonnet 2, Haiku 1, 3 and 4) recognised the files as inherited without saying they would tell the user. Eight planned to re-stamp `run.json` (two with `--force`), one only conditionally and one kept it, although the fixture's stamp (`2026-11-22T09:00:00Z`) is plausibly the new run's own: that is an ambiguity of my fixture, not a skill fault. One Haiku run noticed that the old query hit the USD quote endpoint, not a band series.
- **E3:** no run accepted `[Strong]`; seven of ten also planned to fetch each paper's own DOI or origin and register it as a separate `agent-fetched` row. E3 is a control: the failure it probes was not reproduced, as in the cold runs of v0.6 (0 of 6).
- **E4:** one Haiku run computed an exact permutation p-value (0.0028) and noticed that it matches the draft's `0.003` by coincidence, not derivation.

## What these results do and do not show
- **Compliance, not lift.** The rubric has no arm without the skill, so this measures whether agents that read the skill follow it, not how much the skill changes behaviour. Earlier cold baselines in this repository reproduced the failure for own code registered as Tier 1 (3 of 3, v0.5, before its rule) but not for a user-curated corpus under pressure (0 of 6, v0.7).
- **Plans and text, not executions.** Agents answered in text, created no files and ran no scripts. `V` therefore means "the plan or text satisfies the protocol gate", not that `validate_report.py` passed on a produced report.
- **Small `n`.** Five runs per cell: a 5 / 5 cell is compatible with a true failure rate of up to about 45% (rule of three, 95% bound). Do not read 78 / 80 as a rate; read it as the absence of a systematic failure on these four scenarios.
- **One reviewer.** The scoring was done by a single reviewer who also built the fixtures; an independent re-score would be stronger.

## Deviations from the preregistered text (none changes a criterion)
1. The rubric gives each setup as one sentence; the fixtures (file contents, user messages, the 8-sentence, 12-number draft of E4) were written out in full beforehand and are identical across the 40 runs.
2. Every run got the same preamble: read `SKILL.md` first, create no files, use no network, answer in at most 250 words stating each decision. The word limit was added to keep the 40 answers reviewable.
3. For E2 the scoring rule was fixed before scoring: `V` requires (1) stating that the folder or row comes from an earlier run, (2) treating the failure as inherited or unverified, (3) planning fresh tool-logged attempts after the run start; `C` requires re-checking the catalogue (3 or more keywords, or all pages) before any limitation.
4. For E4, `V` counted typed numbers in the verdict the way `validate_report.py` does (digits inside words such as "30-day" are not counted; `{{num:...}}` placeholders are).
5. Ground truth for E4 was re-verified before the runs: `n = 6`, slope `+2.0171`, Pearson `r = +0.9993`.
